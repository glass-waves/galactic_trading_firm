## the strategy under test (v15, promoted, SHORT-ONLY)

tickers AMZN, AAPL, NVDA, MSFT. one position per ticker at a time. entries allowed 09:30–11:30 ET,
everything flat by 11:55 ET (session_close). sizing 36% of $10,000 per position in these files
(live runs 30%; same trades, sizes scaled). fills are next-bar-open with 3 bps slippage + $0.005 half-spread.

entry windows (all conditions must hold on the bar; fill at next bar open):
- `window:5m thrust short`: composite <= -0.35, s5m <= -0.50, s5m lags BOTH other timescales by >= 0.10 (s5m <= s1m - 0.10 AND s5m <= s1h - 0.10), s1h <= 0.0
- `window:strong core short`: composite <= -0.35, s5m <= -0.40, s1h <= -0.30
scores are in [-1, +1]; composite is a weighted blend of the 1m/5m/1h timescale scores (weights
1m 0.10 / 5m 0.60 / 1h 0.30; no hard gates). negative = bearish. session.entry_cooldown_ms 30000.
blocked_by gate names: entries_blocked, daily_loss_breaker, avoid_first_minutes, no_new_entries_after, entry_cooldown.

exits (evaluated every 1-minute bar, in priority order; first to fire wins; fill next bar open):
- `HardStop`      fixed_pct_stop stop_loss_pct 0.025 (2.5% adverse)
- `TrailingStop`  atr_trailing_stop, 5-minute ATR(14) x 7.0 (very loose — almost never fires)
- `ScoreExit`     composite >= +0.30 while short (score flips bullish)  [scoring.exit_threshold -0.30, direction-aware]
- `MaxHoldTimeout` max_hold_ms 5,400,000 (90 min); if the position is LOSING at the check the limit is
  90-15 = 75 min (loss_reduction_ms 900000); if WINNING the limit is 90+30 = 120 min (profit_extension_ms 1800000)
- `SessionClose`  force_exit_by 11:55 ET
- breakeven_stop monitor: once profit >= 1.5%, stop moves to entry price

## files

### trades: data/v15c_<year>_trades.csv  (years 2022..2026; 2026 ends 2026-09-10)
row_type,date,ticker,direction,entry_time,exit_time,entry_price,exit_price,size,pnl,pnl_pct,hold_duration_ms,exit_reason,entry_reason,candle_pattern,entry_composite,exit_composite,entry_1m,entry_5m,entry_1h,exit_1m,exit_5m,exit_1h,max_composite,max_composite_time,positive_ticks,total_ticks
- use only rows with row_type == "trade". `summary` rows are per-ticker-day totals (pnl in col 10, trades col 12).
- times are UTC rfc3339. ET = UTC-4 (EDT, mar–nov) / UTC-5 (EST). use zoneinfo("America/New_York").
- entry_price / exit_price are the FILLED prices (already include slippage). pnl is dollars, pnl_pct is
  signed fraction in the trade's favour (positive = profit). direction is always Short here.
- exit_reason values: HardStop, TrailingStop, ScoreExit, MaxHoldTimeout, SessionClose.

### per-bar diagnostics: data/v15c_<year>_ticks.csv   (one row per 1-minute RTH bar per ticker per day)
date,ticker,ts,open,high,low,close,volume,vwap,composite,s1m,s5m,s1h,position,unrealized_pct,hold_min,event,entry_reason,blocked_by,near_miss
- `position` is the state BEFORE the bar's signals are applied ("short" or ""), `unrealized_pct` /
  `hold_min` likewise. `event` is "open" (engine signalled entry on this bar → fill next bar open),
  "close" (signalled exit → fill next bar open), or "".
- `blocked_by` is non-empty when a session gate refused entries on that bar (e.g. cooldown, after
  11:30, loss breaker, max positions). `near_miss` is non-empty when NO gate blocked, the composite
  condition of a window passed, but other conditions failed — format "window name: cond1, cond2".
  NOTE near_miss is empty when the composite condition itself failed, so to find bars that
  "almost" qualified you must evaluate the window conditions yourself from composite/s1m/s5m/s1h.
- the 8 trading days BEFORE each date are warm-up and are not in this file; only the target day's bars are.
- the file for a year is ~1M rows (250 days x 4 tickers x 390 bars) → stream it with csv.reader, don't load everything into dicts.

### raw bars: data/bars/<TICKER>.csv   (2022-01-03 .. 2026-09-11, RTH 1-minute)
timestamp,open,high,low,close,volume  — timestamp is UNIX EPOCH SECONDS (UTC). ~440k rows per ticker.
use these for forward paths (what happened after entry / after a missed setup).

## how to report
write a markdown report at .../scratchpad/<your-name>/report.md and return its full text as your final
message. lead with the 3–5 findings that would change a config knob, each with the numbers that back it
and the counter-evidence you checked. prefer tables. be explicit about what you could NOT determine.
avoid recommendations that need new code unless the evidence is overwhelming; the knobs that can be
changed by config alone are: the window condition thresholds above, exit_threshold, stop_loss_pct,
atr multiplier, max_hold_ms / loss_reduction_ms / profit_extension_ms, breakeven trigger_pct,
no_new_entries_after / force_exit_by, entry_cooldown_ms, tickers, sizing.
per-year breakdowns matter: a change that helps 2022 and hurts 2023–2026 is not a win.
