# desk: signals-new — genuinely new triggers added alongside v18

agent `signals-new`, 2026-11-01. 32 ledger runs (31 distinct specs) of the ≈ 80 budget. windows used: `2025h1`
(scaffold check), `2024h2_25h1` (screen), `train` (confirmation). nothing after 2025-06-30 was run or read.

**verdict: no nominations.** none of the five families adds a population that holds up. 2 of 28 screen cells met the
screen gate (added PF ≥ 1.3 with ≥ 20 added trades and no large baseline displacement). both lost money as an added
population on `train`. the useful finding is structural, and it explains HISTORY §E's "added alongside, not loosened" problem:
**a new morning short window on the same four names does not add trades. It pre-empts v18's own entries.**

## method

- every cell is `research/lab/specs/signals-new/<cell>.json` → `research/lab/patches/signals-new/<cell>.json`, all generated by
  `research/lab/patches/signals-new/_make.py` (re-run to reproduce). `_added.py CELL WINDOW` is the additivity check. It splits
  a run's trades into v18-window trades and new-window trades by `entry_reason`, counts baseline trades kept / missing
  (key = date, ticker, entry, exit, pnl), and prints the added population (P&L / trades / PF by year, worst day, exits, tickers)
  and the combined book.
- new morning windows sit at priority 30, after v18's windows and its 1m-noise reject gates. They inherit the gates and
  only fire on a bar where neither v18 window fires.
- the afternoon window needs an opened session. **scaffold** (`scaffold.json`): disable the two v18 windows, re-add them
  as `_am` copies with `entry_before 11:30` and `exit_overrides.force_exit_by 11:55`, and set session 15:30 / 15:55. On `2025h1` it
  reproduces `base/v18` trade for trade: 45 / 45 kept, `lab.py compare` P&L diff +0, correlation 1.00.
- afternoon fade windows fire on the 12:30 bar only (`entry_after 12:30`, `entry_before 12:31`). Their `exit_overrides` are
  `force_exit_by` = entry + hold, `score_exit_threshold −10` (disables the score exit both ways; at −0.30 a fade short would exit
  at once) and `max_hold_ms` = hold, so the 40-minute losing-side limit does not cut the hold short. Priority −5, ahead of the reject
  gates. The pretest has no gates, and the gates are tuned for the thrust.
- the coordinator's pitfall: `disable` on an indicator id does nothing. Checked: every `disable` in this desk names only the two v18
  window actions. No indicator was ever disabled, so no re-run is needed.
- small "baseline changed" counts (3–11) in time-disjoint cells come from sizing drift. Each day's process replays the 8-day
  warm-up, so an afternoon trade during warm-up changes the capital, and with it the share count of a later morning trade. The changed P&L
  matches within a few dollars (for example `pms_x10` train: base side +115, new side +112).

base `v18` on the screen `2024h2_25h1`: **+59 / 97 / PF 1.05**, worst day −123. on `train`: +1179 / 324 / PF 1.32.

## reading

1. **pre-emption is the mechanism (F3, F4, F5).** v18 only knows one position per ticker. A new short window that keys on the
   same falling-name state (a volume spike, a prior-low break, a bearish engulfing) fires a bar or more *before* the thrust/core
   conditions complete. It takes the position, and v18's entry on that thrust never happens. The volume windows kept only 35–69 of
   97 baseline trades. The baseline trades they displaced were worth +285…+425 on the screen, more than the whole base book (+59).
   This is why the added population can look good while the combined book gets worse. `vol_r30_o05` adds PF 1.35 / 94 trades, but combined it is
   −16 / PF 0.99 against base +59. A good part of the "added" P&L is the same move, entered earlier and worse. The same holds
   for the earlier trigger study's "1m-led confirmation is dead / earliest in the thrust is the edge". On these names the thrust state is the edge, and
   anything that reacts to the same tape first only dilutes it.
2. **state-disjoint is the only honest additive design for a morning window**, and it does not pay. Requiring 1h > 0 (both
   v18 windows need 1h ≤ 0) cut the displacement to 4–11 trades. `vol_r20_o05_1hpos` cleared the screen gate: +135 / 33 / PF 1.59.
   On `train` the added population is −224 / 152 / PF 0.87, losing in 3 of 4 years. That is the same "loosen the 1h confirmation" population
   that HISTORY §B1/D6 calls the worst lever, now with a volume tag. The combined book's +1239 vs +1179 on train comes from 33
   changed baseline trades (−235 removed), not from the new window. It is noise, and v18 already has those days.
3. **the afternoon fade is a regime fit (F1).** Two-sided as in the pretest, the long side lost in every cell on 4 names and on the
   34-name pool (pool: −3031 / 1013 at 1.0 %). Engine exits (breakeven 0.5 %, hard stop 2.5 %) are not the pretest's no-stop hold, and the
   hard stop alone cost −1675 to −2139 in the pool cells. The short side on the 4 names looked strong on the screen (1.5 %: +221 / 22 /
   PF 2.69; 1.0 %: +240 / 61 / PF 1.48). On `train` the short-only window is −218 / 239 / 0.91 at 1.0 % and −178 / 84 / 0.82 at 1.5 %, with
   2022–23 negative. This agrees with HISTORY §D3 (every afternoon window loses) and c14's own "fragile" verdict. The engine cannot
   normalise the stretch by the name's trailing range, because `vwap_distance` exposes only raw `dist_pct`. That is a known gap (RQ-10), but the
   4-name raw-threshold cells are close to c14's 4-name variant, and that variant was also 3/5.
4. **gap fade (F2):** the gap-up-plus-fade population loses (PF 0.73–0.83), and adding the thrust shape leaves 5–7 trades a year.
   As the entry screen found, gaps confirm and never lead.
5. **candles (F5):** inside the filters the engulfing still loses (PF 0.61–0.83). The 1h ≤ 0 and three-crows variants are flat on 22–40
   trades. The crows cell's combined +169 comes from one shifted baseline trade (+98), not from the crows trades (+17).

controls: the additivity split *is* the control here. Every "good-looking" added population was checked against the baseline trades it removed.
The train confirmation was run on the two cells that cleared the screen gate, and both failed. A paired `lab.py compare` vs v18 was not
run because no cell reached nomination. The combined train books (+958 / +995 / +1239 vs +1179) are within noise of v18 or below it.

## nominations

**none.** Best of N, stated: N = 28 screen cells across 5 families plus 3 train confirmations. The best train result is
`vol_r20_o05_1hpos` combined +1239 / 450 / PF 1.25 vs v18 +1179 / 324 / PF 1.32. Its added population is PF 0.87, so it is not a
contender. Nothing here should be revealed on the holdout. If the coordinator still wants a "new trigger" finalist for
diversity, my written holdout expectation for every cell in this report is: added population PF ≈ 0.8–1.0, combined book PF at or below its
base. No new-window cell is reported on `2023_25h1`, because the `train` rows above already contain 2023-01 → 2025-06. For example, the
`pms_x10` added population on 2023+24+25h1 is −182, and `vol_r20_o05_1hpos` is −10.

## proposals (engine, not implemented)

- **window lockout / yield:** an `entry_window` option such as `yield_to: [window names], within_ms`. It would suppress the window when a named
  higher-quality window could still fire on this ticker within a horizon. That cannot be known causally, so the practical form is ticker-time
  partitioning: `entry_after` on the new window *later* than the old window's typical fire time, or a state partition as in reading 2.
  Without one of these, any same-state trigger cannibalises v18. Low priority, because reading 2 says the partitioned population has no edge.
- **per-window ticker scope** (`tickers: [...]` on an `entry_window`). Today any window added to a config trades every ticker, so
  a pool-wide window (afternoon fade on 34 names) cannot sit in the same config as the 4-name v18 windows without also opening v18
  on 30 more names. It would need a second book instead. Moot for now (the pool fade loses), but it is a blocker for any future pool trigger.
- **normalised VWAP stretch** (`dist_pct / trailing mean daily range`) on `vwap_distance`. This is RQ-10's request, needed to test c14
  faithfully. Low expected value given the train result above.
